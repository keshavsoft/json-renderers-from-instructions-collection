The spec-repo Story & Type Resolution

Where does type: "table.simple" come from? The story of separating UI blueprints from rendering engines.

The Origin Story

The Problem with Traditional Component Libraries

In most frontend architectures, component logic and HTML structure are coupled together. If you want a table, you write or import a Table component with hardcoded JSX or HTML template strings. If you want a form, you write another component. If schema changes, you update multiple templates.

To solve this, KeshavSoft created spec-repo — a centralized, pure JSON specification repository.

In spec-repo, components do not contain JavaScript render loops, React hooks, or string concatenations. Instead, they are defined purely as declarative blueprint definitions:

1. Base VDOM Skeleton The exact DOM tags, CSS classes (e.g. Bootstrap 5 table classes), and data-role attributes.
2. Instruction Rules Single-pass instructions (buildColGroup, buildHeader) and two-dimensional matrix loops (buildBodyTr, buildBodyCell).
3. Option Modifiers Pluggable transforms (e.g. unshiftSerialToRows, pushToRows for action buttons, tableSearch).

How type: "table.simple" is Resolved in Code

When you pass { type: "table.simple" } to the collection renderer, buildSingleSpec.js performs the dot-separated lookup against spec-repo definitions: 

import { definitions as fallbackDefinitions, spec as fallbackSpec } from "spec-repo";

// type = "table.simple"
const localTypeSplit = type.split(".");
const category = localTypeSplit[0];  // "table"
const variant  = localTypeSplit[1];  // "simple"

// Extracts blueprint from spec-repo definitions
const categoryDef = definitions[category];
const config = (variant && categoryDef?.[variant]) ? categoryDef[variant] : categoryDef;

This blueprint is then handed to json-renderers-run-instructions and json-renderers-run-options to populate it with your data and columns!
